# Forge Symbolic Operator Interpreter Roadmap

Status date: 2026-07-29

Status: Forge-owned planning roadmap; not a runtime activation or canonical
language declaration

Current-state companion:
[`AIWEB_LANGUAGE_CORE_RMC_COUNCIL_BOOTSTRAP.md`](AIWEB_LANGUAGE_CORE_RMC_COUNCIL_BOOTSTRAP.md)

## Purpose

This roadmap describes how the current bounded Language Core bootstrap can grow
into the Forge symbolic operator interpreter and, later, the governed operator
system.  The target is not a chatbot that imitates an LLM.  It is a traceable
system in which exact source, symbolic composition, governed memory, typed
capabilities, deterministic rendering, validation, and operator authority stay
separate and inspectable.

The current bootstrap proves a narrow vertical path.  It does not prove a
complete language, automatic learning, general code construction, tool use, or
an autonomous operator council.  Every later capability in this roadmap must
fail closed until its own typed contract, evidence, tests, and authority gate
exist.

The inspected Google Drive manuscript *The Recursive Manifest Compiler: A
Traceable Symbolic Architecture for Meaning Compilation, Drift-Bounded Novelty,
and Human-Readable Output* is design provenance and a useful architectural
reference.  It is not runtime canon.  Forge-owned schemas, decisions, tests,
manifests, and receipts determine what the running system actually means and
may do.

## Terms that must remain distinct

- **Language Core** preserves exact input and constructs symbolic meaning
  candidates from Forge-owned concepts, senses, predicates, roles, relations,
  and construction rules.
- **RMC semantic memory** is the governed exact-identity evidence layer under
  `memory/rmc_language_core_v1`.  It is not vector memory and does not select a
  meaning merely because words overlap.
- **Recursive Manifest Compiler** is the output-compilation substream that
  binds an already selected meaning, typed result, evidence, gates, and
  provenance into an immutable output manifest.  The name does not grant it
  memory-write or meaning-selection authority.
- **Operator Council** is a fixed, recommendation-only review surface.  It
  cannot select a tool, authorize an action, write memory, or deliver text.
- **Echo** is deterministic full-contract reconstruction and comparison.  It
  is not model self-evaluation or a similarity score.
- **Candidate learning** means deterministic discovery and accumulation of
  proposed symbolic records and replay cases.  It does not mean training model
  weights, creating embeddings, or automatically changing canon.
- **Canonical promotion** is a separate, explicit, receipt-bound operator
  decision after validation.  Candidate discovery never implies promotion.

## Bootstrap versus operating model

### What the bootstrap proves

The installed bootstrap currently proves that Forge can:

1. preserve an operator's exact Unicode source;
2. project source forms without an LLM token stream;
3. construct bounded concepts, senses, predicates, roles, and meanings;
4. apply expectancy, congruity, connectedness, and purport gates;
5. require exact semantic-contract RMC support before Council recommendation;
6. preserve ambiguity and fail closed;
7. compile a selected meaning into an immutable output manifest;
8. render from a closed symbolic grammar;
9. reparse and Echo-check the complete rendered contract; and
10. prove two bounded definition-delivery fixtures through explicit one-time
    operator approval.

Its eight promoted replay fixtures are bootstrap evidence.  They are not a
claim that the proposed semantic charter is canonical or that Forge understands
ordinary English generally.

The first operating slice now sits around that bootstrap at
`POST /api/operator/ask-forge`.  It automatically checks deliverable promoted
exact RMC, invokes the typed read-only status or bounded math provider when
matched, consults retained candidates, and acquires bounded public evidence
only when internal evidence is insufficient.  Candidate answers are visibly
noncanonical; action requests return a plan without execution.

### What the operating model must add

A usable operator system must repeat the same governed structure across many
typed capability families:

```text
operator source
  -> symbolic interpretation
  -> supported operator intent
  -> typed capability producer
  -> typed result or action proposal
  -> immutable result/output manifest
  -> deterministic language realization
  -> full-contract Echo
  -> explicit delivery or action policy
```

The operating model therefore requires more than vocabulary.  It needs a
productive construction algebra, typed result producers, capability routing,
project and source manifests, evidence acquisition, proposal and promotion
workflows, sandbox verification, action authorization, and complete receipts.

## Source-of-truth order

When records disagree, Forge uses the following authority order:

1. **Current Forge-owned accepted decisions and runtime contracts.** These
   declare intended authority boundaries and invariants.
2. **Verified installed implementation, schemas, tests, manifests, and
   receipts.** These prove what the present build actually does.  A conflict
   with level 1 is a defect to reconcile, not permission to choose silently.
3. **Promoted exact RMC records and active Forge registries**, limited to the
   exact scope their contracts declare.  A promoted example does not create a
   universal language rule.
4. **Proposed charters, roadmaps, candidate records, and review queues.** These
   guide work but have no runtime authority merely by existing.
5. **Verified external evidence**, including web material, papers, and Drive
   documents.  These may support a proposal but cannot promote themselves.
6. **Historical AI.Web roadmaps, transcripts, imported packets, model output,
   and unresolved symbolic references.** These are provenance or hypotheses,
   not canon.

Every artifact should declare its status and the authority level it occupies.
If the level cannot be determined, Forge must treat it as untrusted reference
material and hold any dependent decision.

## Permanent operating laws

1. Exact source custody precedes interpretation.
2. Exact character spans are source coordinates, not LLM tokens.
3. No model token stream, subword pieces, numeric token IDs, embeddings,
   vectors, or similarity retrieval may become Forge's semantic foundation.
4. Hierarchical construction precedes meaning selection.
5. Memory evidence may constrain a candidate only through exact declared
   semantic identities and contracts.
6. Meaning precedes output-manifest compilation; the manifest precedes
   rendering; rendering precedes Echo; Echo precedes delivery.
7. A renderer expresses a selected typed result.  It cannot invent a result or
   choose a meaning.
8. The Council recommends.  Forge governs.  A separate operator authorization
   governs any outward effect.
9. Unsupported, ambiguous, conflicting, or unproved cases remain held.
10. Automatic observation may create review candidates only under a declared
    capture contract.  It may never alter canonical grammar, stable RMC, tools,
    code, or permissions.
11. Imported or web evidence is non-executable and cannot define Forge law by
    repetition or source prestige.
12. Every delivered answer, applied action, and promoted memory record must be
    reproducible from its exact manifest and receipts.

## Original input-to-Echo stream

The original operator source must remain recoverable at every stage:

```text
exact operator source
  -> source-custody record and receipt
  -> reversible character/source-field projection
  -> hierarchical construction graph
  -> concept and sense candidates
  -> predicate, participant-role, relation, polarity, speech-act, and purport
  -> expectancy / congruity / connectedness / purport gates
  -> exact-contract RMC evidence evaluation
  -> one selected meaning, or an ambiguity/unsupported hold
  -> recommendation-only Council review
  -> Forge disposition
  -> typed capability result, when the request needs live system information
  -> immutable Recursive Manifest Compiler output manifest
  -> closed symbolic-grammar renderer
  -> exact reparse and full-contract Echo comparison
  -> explicit answer-delivery policy
```

For ambiguity, all admitted alternatives remain preserved.  A clarification is
a governed preview bound to the original evidence.  The operator enters a new
complete source, and Forge recompiles it; Forge never turns an option label into
meaning or silently continues a session.

For status, inspection, comparison, planning, code, or action requests, the
selected request meaning is not itself an answer.  A typed capability producer
must create an independently verifiable result before output compilation.

## Memory-first hierarchy

Memory-first does **not** mean memory-before-source.  The operator's exact
source is always primary custody.  Memory-first means that Forge cannot select,
state, or act on a meaning as trusted merely because a parser or renderer can
form it.  Governed evidence must be evaluated before disposition and output.

The intended evidence hierarchy is:

```text
Forge laws and active semantic/construction registries
  -> promoted exact stable RMC records
  -> approved live/review evidence with explicit lifecycle state
  -> bounded session and clarification-reentry evidence
  -> external web/document evidence proposals
  -> speculative candidates and historical references
  -> EchoForge advisory material
```

Rules for this hierarchy:

- stable, source-backed, operator-approved evidence outranks speculative
  material only inside the semantic scope it proves;
- newer corrections supersede older records through an explicit
  `superseded_by` chain; old records are marked, not deleted;
- conflicting records remain visible and block unique selection until governed
  reconciliation exists;
- raw spelling overlap, frequency, vector proximity, or paraphrase similarity
  does not count as RMC support;
- RMC influence on a selection must be declared in the result, including the
  exact record IDs and `context_used_for_selection` state;
- retrieval must preserve namespace, source, ancestry, lifecycle, and receipt
  boundaries; and
- Ask Forge remains unable to call memory mutation routes.

## Typed capability families replacing legacy LLM roles

The old model paths combined interpretation, context, generation, review, and
sometimes tool or patch proposals.  Forge must replace those responsibilities
with separate typed producers rather than one general text generator.

| Capability family | Legacy model role | Forge-owned replacement | Required typed output |
| --- | --- | --- | --- |
| Ordinary interpretation | Qwen/Ollama request fallback and prompt interpretation | Language Core composition, four gates, exact RMC, ambiguity preservation | `SelectedMeaning` or governed hold |
| Diagnostic explanation | Diagnostic-output analysis and `llm-live-draft` | Diagnostic fact extractor, named rule evaluators, evidence-bound explanation producer | `DiagnosticResultManifest` |
| Engine review | `llm-engine-review-*` | Contract comparison, invariant checks, replay, regression and evidence summarization | `EngineReviewResultManifest` |
| Repair and dependency planning | `generic-repair-*` and `generic-sandbox-dependency-*` | Source inventory, failure classification, dependency graph, bounded repair transformations, sandbox plan | `RepairProposalManifest` |
| Revision planning | `generic-revision-*` | Exact baseline/delta analysis, declared revision rules, candidate change set and replay verification | `RevisionProposalManifest` |
| Command implementation | `forge-command-implement*` | Command schema compiler, capability binding, implementation candidate, preflight and install policy | `CommandImplementationManifest` |
| Tool wrapper and suggestion | `forge-tool-wrap*` and former model tool suggestions | Tool schema inspection, adapter generator from declared templates, permission analysis and compatibility tests | `ToolAdapterProposalManifest` |
| Forge self-suggestion | `forge-self-suggest` | Evidence-backed gap detector and roadmap candidate producer | `BacklogProposalManifest` |
| Natural-language output | Model prose generation | Typed result plus closed renderer and Echo | `OutputManifest` and `EchoReceipt` |

The authoritative blocked-command inventory remains
`agents/forge/llm_authority.py`.  Its 28 commands divide into four engine-review
commands, one live-draft command, nine repair/dependency commands, seven
revision commands, four command-implementation commands, two tool-wrapper
commands, and one self-suggestion command.  Old direct-provider helpers are
transport remnants, not missing capability definitions; they stay fail closed.

EchoForge may still produce explicit advisory material.  If an operator wants
to use that material, it enters Forge through the same untrusted-evidence intake
as any external proposal.  It is never accepted as meaning, proof, permission,
tool routing, patch authority, or memory merely because EchoForge produced it.

## Automatic candidate learning versus canonical promotion

Forge can become more useful from operation without allowing runtime experience
to rewrite its own laws.  Candidate learning should be implemented as an
evidence-producing pipeline:

```text
unsupported, ambiguous, or repeatedly requested exact source
  -> deterministic structural signature
  -> admitted examples and counterexamples
  -> proposed concept/sense/predicate/role/construction/capability delta
  -> provenance and conflict report
  -> generated replay fixtures
  -> isolated validation
  -> review queue
```

Automatic candidate learning may:

- count exact supported and unsupported construction signatures;
- identify a missing sense, inflection, role, relation, grammar construction,
  or typed capability producer;
- preserve examples, counterexamples, ambiguity sets, and provenance;
- propose the smallest registry delta that would cover the evidence;
- generate positive, negative, ambiguity, Unicode, and adversarial replay
  fixtures; and
- estimate coverage gained by a proposal using those fixtures.

It may not:

- silently add a concept, definition, grammar rule, RSOC law, tool, permission,
  or stable memory record;
- infer canonical meaning from frequency alone;
- merge conflicting senses into one record;
- treat a web page, imported document, or advisory model answer as approved;
- present speculative wording as trusted or canonical.  A read-only possible
  answer may be delivered only when it is an exact cited excerpt, remains
  visibly labelled candidate evidence, and passes its candidate-boundary Echo;
  or
- mutate source, code, memory, or the active registry from Ask Forge.

The first persistent possible-answer capture contract is now installed under
`memory/rmc_candidate_answers_v1/candidates`.  It is content-addressed,
idempotent, operator-visible, request-disableable, and declares stable/canonical
writes false.  Exact repeated questions can reuse an existing candidate without
another network request.  This v1 store covers answer evidence only; semantic,
grammar, construction, and capability proposals still require their separate
review and promotion contracts.

Canonical promotion is a different workflow:

```text
candidate proposal
  -> schema and provenance validation
  -> conflict and supersession analysis
  -> deterministic replay corpus
  -> independent verifier
  -> Council recommendation
  -> exact operator approval
  -> content-addressed promotion receipt
  -> isolated load/restart
  -> fresh-process baseline verification
```

The existing exact-language RMC workflow governs semantic evidence records.
A separate construction-promotion workflow is still needed for grammar and
semantic-contract changes.  The two workflows must not be conflated.

## Web and document evidence governance

Web research, Google Drive documents, uploaded archives, papers, and project
notes can help fill factual or conceptual gaps, but they enter as evidence, not
authority.  The target web-evidence envelope should preserve:

- exact URL or document identity and revision when available;
- retrieval time, source title, publisher or owner, and access method;
- a content hash or snapshot identity for the material actually inspected;
- the exact claim being supported or challenged;
- bounded excerpts or structured facts rather than an unscoped document dump;
- source independence, conflicts, uncertainty, and later corrections;
- the proposed Forge concept, sense, relation, law, or capability affected; and
- a non-executable classification that prevents source text from becoming a
  command or instruction.

The acquisition path should be read-only and separated from promotion.  A web
result may create or update an evidence proposal, but a second governed action
must approve any semantic or construction change.  Changed or unavailable
sources must not silently inherit an earlier source's receipt.

No external source can establish an RSOC transformation law merely by naming a
glyph.  Disputed identity, entropy, resurrection, or resonance definitions
remain alternatives until Forge owns one consistent typed law and invariant
proof.  The Google Drive RMC manuscript remains in this evidence tier.

## Why a full A-to-Z lexicon is not a prerequisite

A spelling list is not a language system.  A single spelling may have several
senses, grammatical categories, valencies, participant frames, inflections,
scope behaviors, and domain restrictions.  Adding thousands of flat entries
would increase a count while weakening determinism and creating false support.

Productivity should come from a finite, tested composition system that can
combine known structures, not from preloading every dictionary headword.  The
safe growth unit is a vertical construction slice:

```text
needed source forms
  -> exact senses and inflections
  -> predicate/role frames
  -> one construction contract
  -> one typed capability/result family
  -> positive, negative, ambiguity, Unicode, and adversarial fixtures
  -> deterministic renderer and Echo
  -> governed promotion and delivery policy
```

Coverage must be measured by supported constructions, speech acts, semantic
distinctions, capability families, ambiguity behavior, exact Echo success, and
expected holds.  Raw word count is not a completion metric.

## Productive grammar and runtime unification

Forge should avoid separate ad hoc parsers and renderers for every feature.
One promoted construction contract should provide both the interpretation rule
and its permitted realization rules while preserving the direction of
authority: interpretation selects a meaning; realization never does.

Each construction contract should declare:

- source pattern and exact coverage obligations;
- hierarchical constituents and composition operation;
- allowed concepts, senses, predicates, roles, relations, scope and polarity;
- speech act, purport, tense, aspect, reference, and modification behavior;
- ambiguity and expected-hold cases;
- admissible typed capability targets;
- deterministic output forms and complete inverse-decode obligations;
- version, provenance, lifecycle, supersession, and receipt identities; and
- replay fixtures that exercise both interpretation and realization.

The runtime should converge on four shared registries:

1. **Semantic registry:** concepts, senses, predicates, roles, relations, and
   exact inflection behavior.
2. **Construction registry:** hierarchical composition and inverse realization
   contracts.
3. **Capability registry:** selected request meanings mapped to typed producers,
   required permissions, and allowed result schemas.
4. **Evidence registry:** RMC namespaces, lifecycle, ancestry, supersession, and
   exact support contracts.

The verified-mathematics GP-014/GP-015 path remains a separate bounded domain
until an explicit interface contract proves how its typed math results enter
the common output-manifest and Echo layers.  It must not be merged by shared
words or UI placement alone.

## Governed build sequence

### Gate 0 — Preserve and prove the bootstrap

- Keep the fresh-process eight-fixture verifier green.
- Record the current registry, stable RMC snapshot, receipts, and output
  contracts as a reproducible baseline.
- Add a roadmap coverage report that distinguishes live, bounded, proposed,
  held, and historical artifacts.

Exit condition: the existing definitions, ambiguity holds, RMC evidence,
Council output, renderer, Echo, and delivery behave identically after restart.

### Gate 1 — First live typed result producer — initial slice installed

Implement `Can Forge report status?` as the first non-definition vertical
slice:

```text
selected status-request meaning
  -> read-only Forge status snapshot
  -> typed StatusResult
  -> response manifest
  -> deterministic renderer
  -> full-contract Echo
  -> automatic read-only delivery under the typed status contract
```

The status producer may read only the declared status contract.  It cannot
infer health from prose, mutate state, or route a command.

Current result: `Can Forge report status?` reaches the installed read-only Forge
status provider, result manifest, deterministic status renderer, Echo, and
automatic answer delivery.  Remaining exit work is broader promoted grammar,
stale-snapshot handling, and the full negative mutation corpus.

### Gate 2 — Complete the remaining bootstrap capability results

Add distinct producers for:

1. manifest inspection;
2. declarative system-description results;
3. positive and negative architecture claims backed by exact evidence;
4. RMC-versus-vector-memory comparison; and
5. controlled restatement where restatement is the declared result type.

Exit condition: all eight promoted fixtures produce their correct typed result
class; none are delivered by relabeling a restatement as another result.

### Gate 3 — Productive core grammar

Add one family at a time in this order unless evidence justifies a change:

1. conjunction and coordinated structures;
2. intersective and governed modifiers;
3. tense and aspect needed by status/history results;
4. exact reference and anaphora with explicit unresolved-reference holds;
5. comparison structures; and
6. bounded conditionals and requests for plans.

Each family requires inverse rendering, ambiguity cases, adversarial cases,
Unicode coverage, and a promotion receipt.

Exit condition: coverage grows through reusable composition rather than
fixture-specific branches.

### Gate 4 — Candidate and construction governance — answer-candidate v1 installed

- Extend the installed noncanonical possible-answer envelope to semantic and
  construction proposal families.
- Add proposal, replay, conflict, supersession, review, approval, promotion,
  restart, and rollback receipts for constructions and semantic registry deltas.
- Keep active-registry mutation disabled; answer-candidate capture may remain
  enabled only within its visible bounded namespace and off switch.

Exit condition: a new construction can be proposed from evidence, rejected or
approved, loaded, replayed, and rolled back without hand-editing the registry.

### Gate 5 — Web and document evidence intake — bounded web v1 installed

- Extend the installed read-only source acquisition and content-addressed
  evidence envelopes beyond exact-excerpt answers.
- Preserve conflicts and source revisions.
- Require a separate semantic proposal and operator promotion action.
- Add malicious-instruction, stale-source, changed-content, duplicate-source,
  unsupported-claim, and provenance-loss tests.

Exit condition: external evidence can support a proposal but cannot command
Forge or alter canon.

### Gate 6 — Replace diagnostic, review, repair, and revision model lanes

Build typed result producers in increasing authority order:

1. diagnostic facts and explanation;
2. read-only engine review;
3. dependency and impact analysis;
4. repair proposal;
5. revision proposal; and
6. sandbox verification reports.

Exit condition: the corresponding legacy commands have deterministic typed
replacements or documented retirement, with no provider fallback.

### Gate 7 — Governed code-build stream

Add the code-build pipeline defined below.  Begin with one narrow,
template-governed change family and expand only after negative and rollback
tests pass.

Exit condition: Forge can propose, sandbox, approve, apply, verify, and receipt
one bounded code change without model authority or unscoped filesystem access.

### Gate 8 — Tool adapters and controlled OS action

- Compile wrappers only from explicit tool schemas and approved adapter
  templates.
- Bind every action to capability, project, path, argument, permission, timeout,
  side-effect, recovery, and receipt contracts.
- Keep suggestion, proposal, approval, and execution as distinct events.

Exit condition: no natural-language wording, Council recommendation, web
evidence, or EchoForge advice can directly dispatch a tool.

### Gate 9 — Advanced RMC and RSOC research

- Resolve each glyph definition conflict through a typed law proposal.
- Prove invariants before enabling transformation.
- Add resonance or phase retrieval only when its operands, metric, thresholds,
  failure states, and exact relationship to semantic identity are specified and
  tested.
- Never reintroduce vector similarity under symbolic names.

Exit condition: every enabled transform has an exact law, invariant proof,
deterministic implementation, counterexamples, and no implicit authority.

## Code-build governed stream

The code-building path is a higher-authority capability and must not be hidden
inside the language interpreter or Council.  Its intended stream is:

```text
exact operator request
  -> Language Core selected meaning
  -> typed CODE_CHANGE_PROPOSAL capability
  -> exact project binding and permission scope
  -> read-only source-tree manifest with content hashes
  -> requirement, invariant, dependency, and acceptance-test manifest
  -> one or more bounded implementation candidates
  -> deterministic code renderer or declared transformation library
  -> static checks and policy preflight
  -> ProtoForge isolated sandbox
  -> tests, diff, risk, rollback, and provenance report
  -> recommendation-only code review under a separately admitted Council contract
  -> immutable code-proposal result/output manifest
  -> deterministic explanatory renderer and full-contract Echo
  -> explicit operator approval of one exact candidate and diff
  -> scoped apply transaction
  -> fresh-source verification and tests
  -> apply, verification, and rollback receipts
  -> governed memory proposal for the verified result
```

Required boundaries:

- Project binding, permitted paths, baseline hashes, and requested effects are
  fixed before candidate generation.
- A candidate may not modify files merely because it was generated or passed a
  language Echo.
- The language renderer explains a code manifest; it is not the code renderer.
- The code renderer operates only on a declared transformation schema or
  template family.  Unsupported novel transformations remain held.
- ProtoForge sandbox success is evidence, not apply authority.
- Council recommendation is evidence, not apply authority.
- The current Language Core Council contract cannot silently acquire code-review
  or action authority; any code-review role set needs its own promoted contract.
- Apply requires a separate exact operator token, phrase, nonce, candidate ID,
  diff identity, and current-baseline match.
- Any baseline drift invalidates the approval and requires a new proposal.
- Post-apply verification failure invokes the declared recovery policy and
  produces a failure receipt; it does not conceal or automatically reinterpret
  the result.
- Commit, push, release, package installation, service restart, and deployment
  are separate capability families requiring separate approvals.
- Protected memory records only verified outcomes and their receipts.  Failed
  candidates may enter forensic or review storage but cannot support future
  truth claims.

An externally authored or EchoForge-advised patch may be imported as an
untrusted implementation candidate.  It must traverse the identical source,
scope, sandbox, test, approval, apply, and verification chain.  Authorship never
substitutes for proof.

## Completion criteria for the operator interpreter

The interpreter is ready to be called an operating system component—not merely
a bootstrap—when:

1. its supported construction and capability matrix is explicit and measured;
2. every accepted input reconstructs from exact source without token or vector
   dependence;
3. every selected meaning cites exact construction, semantic, and RMC evidence;
4. ambiguity, missing evidence, unknown references, and unsupported actions
   consistently hold;
5. all delivered wording derives from a typed result manifest and passes
   full-contract Echo;
6. candidate discovery and canonical promotion are technically and visibly
   separate;
7. web, document, and advisory evidence cannot become commands or canon;
8. every former Forge LLM role is replaced by a typed deterministic capability
   or explicitly retired;
9. code and tool effects require sandbox evidence and separate exact operator
   authorization; and
10. complete replay, supersession, rollback, and receipt chains survive a fresh
    process restart.

Completing a dictionary is deliberately absent from these criteria.  The goal
is a governed productive symbolic operator, not a large but semantically flat
word list.
